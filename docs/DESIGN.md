# lawdesk 설계 문서

법률사무소의 로컬 문서 폴더를 **오프라인으로** 색인해 전문검색하는 데스크톱 도구.

- 대상 사용자: 비개발자(변호사·사무직원)
- 배포 형태: 윈도우 실행파일 1개
- 절대 조건: **네트워크 미사용**

---

## 1. 왜 이 형태인가

### 1.1 문제

법률사무소 문서 폴더에는 계약서·판결문·등기부등본·증거자료가 수천 건 쌓인다.
윈도우 탐색기 검색은 파일명만 훑고, PDF 본문은 찾지 못한다. 스캔본은 더더욱 안 된다.
"작년에 봤던 그 손해배상 한도 조항이 어느 계약서에 있었지?" 를 해결할 방법이 없다.

### 1.2 제약이 설계를 결정했다

| 제약 | 설계에 미친 영향 |
|---|---|
| **비밀유지의무** (변호사법 제26조) | 네트워크 코드 자체를 넣지 않음. LLM 요약 미채택. 서버는 루프백 바인딩 |
| **사용자가 비개발자** | 설치 프로그램·런타임·DB 서버 없음. exe 더블클릭이 전부 |
| **문서 대부분이 PDF/DOCX, 일부 스캔본** | 텍스트 추출 3종 + OCR 파이프라인 |
| **원본을 건드리면 안 됨** | 문서 폴더는 읽기 전용. 인덱스는 사용자 데이터 폴더에 별도 보관 |

### 1.3 채택하지 않은 대안

| 대안 | 기각 사유 |
|---|---|
| 옵시디언 + 플러그인 | 마크다운 전용. docx/pdf 본문을 읽지 못한다. vault 설정·플러그인 설치를 비개발자에게 요구 |
| PostgreSQL + pg_trgm | 사용자 PC에 DB 서버 설치가 필요. 기본 전문검색에 한국어 파서가 없다 |
| Electron | Node+Chromium 내장으로 150MB+. 리눅스에서 크로스빌드가 번거롭다 |
| Python + PyInstaller | 크로스컴파일 불가 — 윈도우 PC에서만 빌드된다 |
| LLM 요약 (기본 기능) | 비밀유지의무 위반 소지. 구조 추출로 충분히 대체 가능 |
| 로컬 LLM (Ollama 등) | 수 GB 배포 + 사양 요구. "exe 하나" 목표와 충돌 |

**선택: Go + SQLite(FTS5) + 임베드 웹 UI.**
순수 Go 스택이라 cgo 없이 리눅스에서 윈도우 exe 를 만들 수 있고, 런타임 설치가 0이다.

## 2. 전체 구조

```
                    ┌─────────────────────────────────┐
   브라우저 ◄──────►│  localhost:7777 (루프백 전용)    │
   (임베드 UI)      │  net/http + embed.FS            │
                    └───────────────┬─────────────────┘
                                    │
                    ┌───────────────▼─────────────────┐
                    │  scan.Indexer                   │
                    │  워커 N개 병렬 추출 → 직렬 쓰기  │
                    └───────┬─────────────────┬───────┘
                            │                 │
              ┌─────────────▼──────┐   ┌──────▼──────────────┐
              │ extract.Registry   │   │ index.DB (SQLite)   │
              │  ├ docx (내장)     │   │  docs      메타데이터│
              │  ├ plain(내장)     │   │  docs_fts  trigram   │
              │  └ pdf → mutool    │   └─────────────────────┘
              │        └ OCR → tesseract
              └────────────────────┘
```

프로세스 하나, 파일 하나, 포트 하나. 외부 연결 없음.

## 3. 텍스트 추출

### 3.1 포맷별 전략

| 포맷 | 방법 | 근거 |
|---|---|---|
| `.docx` | `archive/zip` + `encoding/xml` 스트리밍 | 표준 라이브러리만으로 충분. 제목 스타일(`w:pStyle`)이 남아 있어 목차를 복원할 수 있다 |
| `.txt .md .csv` 등 | 직접 읽기, UTF-8 실패 시 CP949 폴백 | 국내 사무실 파일에 CP949 메모가 흔하다 |
| `.pdf` (텍스트) | `mutool draw -F txt` 페이지 단위 | 순수 Go PDF 라이브러리는 한글 CID 폰트에서 깨진다. MuPDF 는 검증돼 있다 |
| `.pdf` (스캔) | `mutool` PNG 렌더 → `tesseract` | 아래 3.3 |

`.hwp` 는 이번 범위에서 제외했다(대상 클라이언트 문서에 거의 없음).
필요해지면 `extract.Extractor` 인터페이스에 구현체 하나를 추가하면 된다 — 나머지 계층은 손대지 않아도 된다.

### 3.2 스캔 문서 판별

페이지별로 텍스트를 뽑아 **공백 제외 40자 미만**이면 이미지로 간주한다.

측정값 — 텍스트 PDF 1,752자 / 스캔 PDF 0자. 경계가 뚜렷해 오판 위험이 낮다.
0이 아니라 40으로 여유를 둔 이유는 스캔본에도 머리말·페이지번호가 텍스트로 박혀 몇 글자 나오는 경우가 있어서다.
반대 방향 오탐(표지처럼 원래 글자가 적은 페이지)은 OCR 을 한 번 더 돌릴 뿐 결과가 틀리지는 않는다.

한 문서 안에 텍스트 페이지와 스캔 페이지가 섞이면 `mixed` 로 표시한다
(계약서 본문 + 별지 스캔은 실무에서 흔하다).

### 3.3 OCR 파라미터는 측정으로 정했다

합성 스캔본(기울임·노이즈·JPEG 열화·직인 포함)으로 실측한 결과:

| DPI | PSM | 문자 정확도 | 검색어 재현율 |
|---:|---:|---:|---:|
| 150 | 3 | 95.0% | 87.5% |
| **150** | **6** | **98.1%** | **100%** |
| 300 | 3 | 86.6% | 62.5% |
| 300 | 6 | 98.5% | 100% |

두 가지가 반직관적이었다.

1. **PSM 3(기본값)이 나쁘다.** 다른 문서에서는 정확도가 **37%** 까지 떨어졌다.
   표와 세로 정렬이 많은 한국 법률 서식에서 자동 페이지 분할이 오작동한다.
   PSM 6(단일 텍스트 블록)으로 바꾸면 96%대로 회복된다.
2. **300 DPI 는 이득이 없다.** 시간·메모리만 3배 쓰고 정확도는 같거나 나쁘다.

언어는 `kor` **단독**이다. 영문 계약서를 고려해 `kor+eng` 를 시험했으나
등기부등본 정확도가 98.1% → 93.1% 로 떨어졌다 — 영문 모델이 노이즈가 있는
한글 구간에서 경합해 직인 근처 글자를 라틴 문자로 오인한다.
영문 스캔본이 많은 환경이라면 설정에서 바꿀 수 있게 열어 두었다.

> ⚠️ **이 숫자를 그대로 믿으면 안 된다.** 테스트 스캔본은 합성이다.
> 실제 문서에는 접힌 자국, 복사기 얼룩, 손글씨 메모, 글자 위에 겹친 도장이 있다.
> 현장 정확도는 **90% 내외**로 잡는 것이 안전하다.
> `testdata/measure_ocr.py` 에 측정 하네스를 남겨 두었으니 실제 문서로 다시 재면 된다.

속도는 페이지당 **0.41초**(150dpi/psm6). 500쪽 문서가 단일 스레드로 3.5분,
병렬로 1분 미만이다.

### 3.4 제목 추출 — 첫 줄을 그냥 쓰면 안 된다

초기 구현은 본문 첫 줄을 제목으로 삼았다. 등기부등본에서 제목이 `ro} 번즈` 로 나왔다.
상단 직인이 먼저 인식된 것이다.

그래서 앞쪽 15줄을 훑으며 글자 구성을 본다:

- 유효 문자(한글·라틴·숫자·표제용 문장부호) 비율 ≥ 80%
- **한글 완성형 음절** ≥ 3 또는 라틴 문자 ≥ 5

호환 자모(`ㅎ` 등)를 한글로 세지 않는 것이 핵심이다.
OCR 은 뭉개진 글자를 낱자 자모로 자주 뱉는데, 정상 표제에는 낱자가 거의 없다.
조건을 만족하는 줄이 없으면 빈 값을 돌려주고 호출측이 파일명을 쓴다.

## 4. 검색

### 4.1 trigram 토크나이저

한국어는 공백 기반 토크나이저가 잘 듣지 않는다. 조사가 붙고("계약서를"),
복합어가 붙어 다니기("손해배상책임") 때문이다.
SQLite FTS5 의 `trigram` 토크나이저는 3글자 단위로 쪼개 색인하므로
어절 중간 부분일치와 사건번호 검색을 모두 커버한다.

검증된 질의:

| 질의 | 성격 | 결과 |
|---|---|---|
| `손해배상` | 일반 단어 | ✅ |
| `배상책임` | 어절 중간 부분일치 | ✅ |
| `2021다12345` | 사건번호 정확검색 | ✅ |
| `고합987` | 사건번호 부분 | ✅ |
| `제7조` | 조문 번호 | ✅ |
| `집행을 유예` | 구문 검색 | ✅ |
| `근저당권설정` | **스캔 PDF 내부**(OCR 경유) | ✅ |

### 4.2 두 가지 함정과 대응

**FTS5 연산자 충돌.** `-`, `"`, `(`, `)`, `*`, `:` 는 질의 문법으로 해석된다.
사용자가 `Non-Disclosure` 를 치면 `no such column: Disclosure` 로 터졌다.
전체를 큰따옴표로 감싸고 내부 따옴표를 두 번 반복해 이스케이프한다.
부수 효과로 모든 질의가 구문 검색이 되는데, 조문·사건번호를 원문 그대로 찾는
법률 문서 검색에서는 오히려 기대에 맞는다.

**3글자 미만은 색인되지 않는다.** trigram 의 구조적 한계다.
`지급` 같은 2글자 질의는 `LIKE '%지급%'` 로 우회한다.
인덱스를 못 쓰므로 느리지만 정확하고, UI 에 "부분일치" 라고 표시한다.
3글자 이상인데 결과가 0건일 때도 LIKE 로 한 번 더 확인한 뒤 결과를 돌려준다.

### 4.3 파일명도 본문에 함께 색인

`임대차` 로 검색했을 때 본문에 그 단어가 없어도 파일명이
`임대차계약서_테헤란로501호.docx` 면 찾아져야 한다.
그래서 FTS 의 `body` 컬럼에 `상대경로 + 제목 + 본문` 을 함께 넣는다.

## 5. 데이터 모델

```sql
docs                          -- 파일당 1행, 메타데이터
  id, path(UNIQUE), rel_path, dir, name, ext,
  size, mtime,                -- 증분 인덱싱 판단 근거
  kind,                       -- native | scanned | mixed | empty
  title, summary, outline(JSON), warnings(JSON),
  pages, ocr_pages, text_len, indexed_at

docs_fts USING fts5(title, body, tokenize='trigram')
  -- rowid = docs.id 로 조인. 본문은 여기에만 저장해 중복 보관을 피한다.
```

인덱스 DB 는 문서 폴더가 아니라 **사용자 데이터 폴더**에 둔다
(`%APPDATA%\lawdesk\index.db`). 원본 폴더를 어지럽히지 않기 위해서다.

스키마가 바뀌면 `schemaVersion` 을 올린다. 버전이 다르면 인덱스를 통째로 버리고
다시 만든다 — 인덱스는 언제든 재생성 가능한 파생 데이터라서 안전하다.

## 6. 증분 인덱싱

크기와 수정시각이 **둘 다** 같으면 이미 색인된 것으로 보고 건너뛴다.
사라진 파일은 인덱스에서 지운다.

실측: 9개 문서 재색인 시 9건 전부 skip, **0ms**.
첫 실행만 오래 걸리고 이후에는 즉시 끝난다.

병렬 구조는 이렇게 나눴다.

```
파일 목록 ──► jobCh ──► 워커 N개 (추출: CPU 바운드, OCR 포함)
                            │
                            └──► docCh ──► 단일 라이터 (SQLite 쓰기)
```

추출은 병렬, 쓰기는 직렬이다. SQLite 는 다중 쓰기 연결에서 `SQLITE_BUSY` 를
내기 쉬운데, 쓰기를 한 곳으로 몰면 잠금 경합이 아예 없어진다.
워커 수는 `CPU-1`(최대 8)로 잡아 사용자 PC 가 먹통이 되지 않게 한다.

건너뛰는 대상:
- 폴더 — `.git`, `node_modules`, `$RECYCLE.BIN`, `System Volume Information` 등
- 파일 — `~$계약서.docx`(워드 잠금 파일), `Thumbs.db`, `desktop.ini`, `*.tmp`

`~$` 파일은 실제 사무실 폴더에 반드시 있고, 열어봐야 본문이 없어 에러만 난다.

## 7. 폴더 선택 — 브라우저로는 불가능하다

`<input type="file" webkitdirectory>` 는 쓸 수 없다.

- 브라우저가 **실제 경로를 주지 않는다.** 상대경로 목록만 온다
- 파일을 **브라우저 메모리로 업로드**한다. 수천 건을 올리는 건 불가능
- 우리는 파일을 *제자리에서* 읽어야 한다

File System Access API(`showDirectoryPicker`)도 마찬가지다.
디렉터리 핸들은 브라우저 안에만 존재하고 Go 백엔드는 접근할 수 없다.

**해결: 백엔드가 OS 네이티브 대화상자를 띄운다.**
앱이 로컬에서 도니까 가능한 방법이다.

```
브라우저 ──POST /api/pick-folder──► Go 백엔드
                                      └─ SHBrowseForFolderW (win32)
브라우저 ◄──{"path":"D:\\법무팀"}─────┘
```

`IFileOpenDialog`(최신 스타일) 대신 `SHBrowseForFolderW` 를 쓴 이유는
COM vtable 호출을 손으로 짜는 것보다 실패 지점이 적기 때문이다 —
윈도우에서 직접 시험할 수 없는 상황에서 안전한 선택이다.
`BIF_NEWDIALOGSTYLE` 로 크기 조절과 새 폴더 만들기는 지원한다.
UI 에는 경로 직접 입력란을 항상 함께 두어, 대화상자가 실패해도 막히지 않게 했다.

## 8. 보안 경계

문서가 계약서·사건기록이므로 유출 경로를 구조적으로 차단했다.

| 조치 | 위치 |
|---|---|
| 네트워크 코드 없음 | 추출·색인·검색 전 경로에 HTTP 클라이언트가 없다 |
| 루프백 바인딩 강제 | `main.go` 가 비루프백 주소를 거부한다 |
| 요청 단계 재확인 | `localOnly` 미들웨어가 비루프백 `RemoteAddr` 을 403 처리 (이중 안전장치) |
| `Cache-Control: no-store` | 문서 내용이 브라우저 디스크 캐시에 남지 않게 |
| 원본 읽기 전용 | 문서 폴더에 아무것도 쓰지 않는다 |
| 외부 도구 타임아웃 | 손상된 PDF 로 프로세스가 멈춰도 90초에 회수 |

LLM 요약을 기본 기능에서 뺀 것도 같은 이유다.
필요하다면 나중에 **명시적 옵트인 + 전송 경고**를 붙여 추가할 수 있으나,
이 클라이언트에게는 권하지 않는다.

## 9. 배포

### 9.1 단일 exe

Go 바이너리(약 11MB)에 웹 UI 를 `embed.FS` 로 넣고,
`mutool.exe` / `tesseract.exe` / `kor.traineddata` 는 `internal/bundle/assets/` 에서
빌드 시 임베드한다. 실행하면 사용자 캐시 폴더에 풀어 쓴다
(내용 해시를 폴더명에 넣어, 앱을 업데이트하면 새 폴더에 풀린다).

"zip 을 풀고 폴더 구조를 유지하라"는 안내는 현장에서 반드시 깨진다.
파일 하나여야 안전하다.

서드파티 바이너리는 **저장소에 커밋하지 않는다** — 용량(60~80MB)과
재배포 라이선스 때문이다. `scripts/fetch-tools.sh` 가 준비를 돕는다.
assets 가 비어 있어도 빌드는 되며, 그 경우 앱은 `PATH` 와 실행파일 옆 `bin/` 에서 도구를 찾는다.

### 9.2 SmartScreen

서명 없는 exe 는 "Windows에서 PC를 보호했습니다" 경고가 뜬다.
비개발자는 여기서 대부분 막힌다.

- 무료: "추가 정보 → 실행" 안내 이미지를 함께 전달
- 확실: 코드 서명 인증서 구매(연 20~40만원)

### 9.3 윈도우 검증

도커로는 불가능하다 — 윈도우 컨테이너는 윈도우 호스트 커널이 필요하다.

| 단계 | 방법 | 상태 |
|---|---|---|
| 로직 | 리눅스에서 실행 (OS 무관) | ✅ 완료 |
| 크로스컴파일 | `GOOS=windows go build` | ✅ amd64/arm64 |
| Wine 스모크 | `wine lawdesk.exe` | ✅ 기동·API·UI 확인 |
| 윈도우 VM | QEMU/KVM + Win11 평가판 | ⬜ 릴리스 전 |
| 실제 PC | 클라이언트 환경 | ⬜ |

**Wine 통과 ≠ 윈도우 통과.** 특히 아래는 실제 윈도우에서 확인해야 한다:

- `SHBrowseForFolderW` 폴더 선택 대화상자 (GUI 필요, Wine 헤드리스에서 미검증)
- 한글 경로·UNC 경로(`\\서버\공유폴더`) 처리
- 브라우저 자동 실행
- 번들 도구 추출 및 실행

## 10. 알려진 한계

| 한계 | 영향 | 대응 |
|---|---|---|
| OCR 정확도는 실제 문서에서 더 낮다 | 스캔본 일부가 검색에 안 걸릴 수 있음 | 실문서로 재측정 후 기대치 합의 |
| `.hwp` 미지원 | 한글 문서 검색 불가 | 필요 시 Extractor 추가 |
| 폴더 선택 대화상자 미검증 | 버튼이 동작하지 않을 수 있음 | 경로 직접 입력란 상시 제공 |
| 실시간 감시 없음 | 새 문서는 재색인해야 반영 | 증분이 빨라서 부담은 작음 |
| 요약이 추출식 | 문서를 "이해한" 요약은 아님 | 의도된 선택(비밀유지) |
| 대용량 미검증 | 수만 건 규모 성능 미측정 | 실데이터로 확인 필요 |

## 11. 확장 지점

- **새 포맷** — `extract.Extractor` 구현 후 `DefaultRegistry` 에 등록. 다른 계층은 무변경
- **메타데이터 추출** — 사건번호·법원명·선고일자를 정규식으로 뽑아 필터로 제공
- **LLM 요약** — `Doc.Summary()` 를 대체하는 옵션. 반드시 옵트인 + 경고
- **실시간 감시** — `fsnotify` 로 변경 감지 후 증분 색인
- **문서 미리보기** — PDF.js 임베드 또는 mutool 로 썸네일 생성
